## 1. 原版 autoresearch 的核心不只是循环

根据 Karpathy 的 [README](https://github.com/karpathy/autoresearch/blob/master/README.md) 和 [program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)，关键思想包括：

1. **很窄的可变面**：代理只改 `train.py`。
2. **固定评估面**：`prepare.py`、数据、tokenizer、评价函数不可修改。
3. **固定计算预算**：每次训练固定约 5 分钟，使候选在同一平台上可比较。
4. **先测 baseline**。
5. **机械指标决定保留或回滚**：`val_bpb` 更低才推进。
6. **不断循环，直到人类手动终止**。
7. **失败后能看日志、修复或跳过**。
8. **人类主要编写 `program.md`**：真正被“编程”的是研究组织和研究策略，而不只是模型代码。
9. 还有弱形式的研究判断：VRAM、复杂度、简洁性，不完全等价于单纯数值爬山。

这个项目完整抓住了第 1–5 项的核心骨架，但对第 6–9 项做了明显改写。

## 3. 影响“真正无人值守 autoresearch”的主要缺口

### P0：一次提案错误会终止整个研究运行

`src/controller.ts:466-485` 中，以下情况都会直接把 run 置为 `round-failed`：

- proposal child 没有调用 report；
- report 重复、格式错误或过大；
- 没有产生代码变更；
- 改到了 forbidden/protected path；
- proposal agent 路由或能力异常；
- handoff 过大。

测试也明确固定了这个行为，例如：

- `tests/controller.spec.ts:2001-2008`
- `tests/controller.spec.ts:2176-2178`

这与原版的无人值守目标差异很大。原版明确要求：

- 简单错误就修复并重跑；
- 根本失败就记录 crash、回滚并继续；
- 不要因为一次失败停下来等待人类。

当前实现只对**已进入 evaluator 的、可证明进程树静止的特定失败**继续下一轮；proposal/report/path validation 失败仍会结束整个 run。

**影响**：一个不稳定的模型输出就可能让整夜实验在第一轮停止。

**建议**：将安全可分类的 proposal 失败也定义成消耗一次 ordinal 的失败实验，恢复 accepted worktree 后继续；可增加很小的每轮 proposal retry 上限，但不能无限重试。

---

### P0：下一轮缺少足够的故障诊断信息

现在研究记忆已经比旧实现好很多：

- 保存 hypothesis；
- 保存 intended edits；
- 保存 implementation summary；
- 保存 candidate commit、changed paths、diff stats；
- 保存 metric、decision、结构化 failure facts。

但 `src/agent.ts:166-204` 的 handoff 仍不提供：

- evaluator 的明确 metric 名称和 minimize/maximize 方向；
- evaluator 文件和只读 benchmark 契约；
- 失败的受控诊断摘要；
- rejected candidate 的结构化具体差异；
- stderr/stack trace。

Proposal child 也没有 Git/Bash 工具，不能读取 rejected commit 或 evaluator artifact。

例如候选因一个 TypeScript 语法错误退出，下一轮大致只知道：

```json
{
  "failure": {
    "code": "exit",
    "exitCode": 1
  }
}
```

它不知道错误文件、行号和异常文本。原版则要求直接读取 `run.log` 尾部并尝试修复。

**影响**：系统能“继续”，但很难真正从失败中学习；容易重复试验或放弃本可修复的思路。

**建议**：

- 提供 Host 生成、严格限长、允许字段枚举的 diagnostic summary；
- 暴露 metric 名、方向和只读 evaluator 文件列表；
- 提供结构化 rejected diff summary；
- 不应直接注入任意原始 stderr，避免秘密泄漏和 prompt injection。

---

### P0：真实研究效果尚未证明

现有测试证明的是：

- orchestration 正确；
- Git/SQLite/恢复正确；
- DSH composition 正确；
- deterministic fake evaluator 的 accept/reject 正确。

但没有看到：

- 使用真实 DeepSeek 模型执行多轮研究；
- 在真实 benchmark 上超过 baseline；
- 20/50/100 轮运行的有效候选率；
- proposal failure rate、重复实验率；
- crash 后实际恢复研究方向的案例；
- 与普通单 agent 或 Karpathy 原流程的比较。

集成测试使用的是确定性测试 adapter 和 evaluator。这足以证明**机制可执行**，不能证明**研究组织有效**。

因此目前不能宣称：

> “它已经验证为能自主产生有效科研改进的 autoresearch 系统。”

只能宣称：

> “它已经验证为可执行、可恢复的 metric-driven 实验控制器。”

## 4. 科学可比性仍依赖部署者

### 4.1 timeout 不是固定计算预算

README 已诚实说明：`timeout_ms` 只是 watchdog，不是固定 steps、epochs、FLOPs、CPU/GPU time。

这意味着候选可以通过改变：

- batch size；
-评估频率；
- 数据量；
- warmup/compile 行为；
- 提前退出；
- 缓存策略；

获得不可比结果，除非 evaluator 自己固定并验证计算方法。

原版的 5 分钟训练预算是实验定义本身；本项目只是允许 Host 自己实现这个定义。

**结论**：科学公平性是**条件通过**，不是插件自动保证。

### 4.2 没有 evaluator/GPU 级资源锁

现有并发限制是：

```text
maxActiveRunsPerRepository
```

它只能防止同一仓库并发。两个仓库仍可同时竞争同一 GPU/CPU/磁盘，破坏 baseline 与 candidate 的可比性。

需要 evaluator registration 级别的 resource/concurrency key，或部署层明确串行化 GPU evaluator。

## 5. Provenance 很强，但不是完整运行环境复现

当前 provenance 绑定了：

- argv 文本；
- evaluator 文件 hash；
- local dataset 文件 hash；
- external dataset 声明 digest；
-显式环境值 hash；
- metric、direction、parser version；
- policy hash。

没有内容绑定：

- 实际解析出的 interpreter/executable 二进制；
- Node/Python/CUDA/shared-library 版本；
- subprocess provider 实现；
- container/image；
- GPU 型号、driver；
- evaluator 间接加载但未声明的依赖；
- external dataset 实际字节是否对应所声明 digest。

因此：

- 同一次短运行内的证据较强；
- 跨机器、跨镜像或长时间 resume 的完全复现仍是 Host 责任。

这不是当前文档中的虚假声明，但应避免把它称为“完整可复现环境”。

## 6. 与 Karpathy 思想的明确非等价点

这些多为有意产品决策，不一定是 bug：

1. **有限运行，而非 LOOP FOREVER**  
   默认 20，部署默认上限 100，不自动续跑。

2. **没有 `program.md` 式研究组织接口**  
   人类只能提交 `objective` 和 advisory `constraints`；研究 prompt 主要硬编码在 `src/agent.ts`。

3. **每轮是新的 proposal child**  
   依靠压缩后的 durable memory 传递经验，不是同一个长期研究者上下文。

4. **acceptance 只有一个 scalar metric**  
   `constraints` 不参与 Host accept/reject；simplicity、VRAM、代码质量必须编码进 evaluator 或依赖模型自律。

5. **不允许代理自己执行 evaluator**  
   这是安全性增强，但也减少了代理调试能力。

所以它更像：

> “安全收紧后的 bounded black-box optimizer”

而不是原版完整的：

> “由人类编写研究组织程序、长期自主调试和探索的研究代理”。

## 7. 安全边界

### 做得正确的部分

- 模型不能提交任意 evaluator command/env；
- evaluator/local dataset 文件被保护；
- repo target 不能逃出 parent Agent repository；
- Git hook、filter、diff driver 等可执行 Git config 被阻断；
- 进程树取消后必须确认 quiescence；
- 未知状态 fail closed；
- secret 只进入 spawn，持久化表面使用 hash/精确值替换。

### 明确没有提供的部分

README 的声明是准确的：

- 不通过 DSH sandbox seam 运行 evaluator；
- Git worktree 不是 OS sandbox；
- candidate code 可以访问同 UID 文件、网络和进程；
- 不能用于 hostile candidate；
- external sandbox 必须由部署另外提供。

另外，“只有收到 direct human 明确请求才调用 autoresearch”目前只是 `src/index.ts:33` 的 system-prompt guidance，`execute()` 没有 Host 级授权检查。它依赖 DSH 的通用 approval/tool policy。

因此：

- **对可信项目代码**：可用。
- **对不可信候选代码**：不可用。
- **昂贵运行的强人工授权**：插件本身未强制。

## 8. 发现的具体工程问题

### 8.1 当前 coverage gate 是红的

实际运行：

```text
pnpm run check
```

结果：

- 11 个测试文件通过，1 个跳过；
- 522 tests passed，7 skipped；
- typecheck 通过；
- build 通过。

但：

```text
pnpm run test:coverage
```

退出码为 1：

```text
All files lines:        95.94%
src/controller.ts lines: 90.87%
required threshold:      92%
```

因此当前不能说“所有质量门均通过”。`pnpm run check` 也没有包含 coverage。

仓库内未发现 `.github` workflow；即使测试非常全面，当前也没有仓库内 CI 自动阻止这种门禁回退。

**建议**：补齐 controller 未覆盖的实际状态分支，而不是直接降低阈值；并把 `check`、coverage、release smoke 放入 CI。

### 8.2 evaluator 预算被错误复用于 Git 控制面

`src/controller.ts:54-62`：

```ts
const timeoutMs = input.timeout_ms ?? config.defaultTimeoutMs
const gitOptions = {
  timeoutMs,
  maxStdoutBytes: config.maxStdoutBytes,
  maxStderrBytes: config.maxStderrBytes,
  ...
}
```

结果是：

- 文档称为“per-attempt evaluator watchdog”的 `timeout_ms`，同时限制所有 Git 操作；
- evaluator stdout/stderr caps 同时限制 `git status`、`worktree list`、diff 等控制命令。

在大型仓库或用户设置很短 evaluator timeout 时，Git discovery/commit/reconciliation 可能意外超时或 output-limit。

**建议**：拆成独立部署配置：

```text
gitTimeoutMs
gitMaxStdoutBytes
gitMaxStderrBytes
```

Evaluator policy 不应改变控制面的 Git 可靠性。

### 8.3 安装后默认不可运行，配置引导不足

`evaluatorRegistrations` 默认是空数组。安装和加载成功，但任何新 run 都必须先由 Host 配置 evaluator。

这本身正确，但 README 没有给出一个完整可复制的 profile `cordis.patch.yml` evaluator registration 示例。考虑到 whole-row patch 和多个必填字段，这会显著增加首次使用成本。

## 最终判定

### 可以接受的项目声明

> “A bounded, metric-driven autoresearch plugin for DeepSeek Harness.”

**成立。**

### 目前不应使用的声明

> “Karpathy autoresearch 的完整等价实现。”

**不成立。**

> “已经证明能够长时间无人值守地产生真实研究改进。”

**证据不足。**

> “提供安全的任意候选代码执行环境。”

**不成立，且项目文档也明确否认。**

5. 增加 evaluator resource lock 和更完整 runtime provenance。
6. 修复 coverage gate，并加入 CI。
7. 可选加入 Host 强制的人类授权与 sandbox execution contract。
