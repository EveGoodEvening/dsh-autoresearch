## 结论

**还不能说“真正完成了 DeepSeek Harness 中可信、无人值守的 autoresearch 插件”。**

更准确的定位：

> 当前项目是一个完成度很高的 **DSH 原生、有界、可审计、可恢复的实验执行控制器**；但还不是一个足够可信、能持续自主研究的 Karpathy-style autoresearch 系统。

分项判断：

| 维度 | 结论 |
|---|---|
| DSH 插件安装、Bundle、Profile 集成 | 达标 |
| baseline → candidate → metric → keep/reject | 达标 |
| Git worktree 隔离、SQLite 证据、恢复 | 很强 |
| evaluator/data 真正不可篡改 | **未达标** |
| evaluator 选择由可信 Host 控制 | **未达标** |
| 失败后继续自主搜索 | **未达标** |
| 跨轮次研究记忆 | **未达标** |
| Karpathy 的长期无人值守循环 | 仅部分实现，且有意改为 bounded |

所以总体结论是：**工程骨架成立，核心闭环也真实运行；但“可信 evaluator + 持续研究”这两个 autoresearch 的核心条件尚未成立。**

## 一、autoresearch 真正的理念

Karpathy 的设计重点并不是“让模型反复改代码”，而是建立一个受控的实验搜索闭环：

1. **固定、不允许修改的 evaluator**
   - `prepare.py`、评估方法、数据、时间预算属于 ground truth。
   - Agent 只能修改 `train.py`。

2. **固定计算预算**
   - 每个实验固定训练 5 分钟。
   - 防止通过增加运行时间换取指标，让候选结果可比较。

3. **单一机械指标**
   - `val_bpb`，越低越好。
   - Agent 提想法；机械指标决定接受或丢弃。

4. **baseline-first**
   - 第一轮必须测原始代码。
   - 后续所有结果都相对当前 best 判断。

5. **保留成功、回滚失败**
   - 改进就推进分支。
   - 持平或退化就 reset。
   - crash 被记录，但不应终止整个研究流程。

6. **长期自治**
   - 原始指令明确要求开始后不要反复询问人类。
   - 循环直到人工终止。

7. **实验记忆**
   - `results.tsv` 不仅记录 commit 和 metric，也记录 `status`、显存和实验描述。
   - 后续实验必须知道“之前试过什么、为什么失败”。

8. **研究组织本身也是可编程对象**
   - 人类主要修改 `program.md`，即“研究组织的程序”。
   - Agent 负责执行实际实验搜索。

来源：

- [Karpathy autoresearch README](https://github.com/karpathy/autoresearch)
- [原始 program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)
- [DeepSeek Harness 架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

# 三、阻断完整目标的主要问题

## P1：evaluator 实际仍由模型选择，并通过 raw subprocess 执行

这是当前最严重的信任边界问题。

`evaluation` 和 `environment` 都是模型可填写的 tool 参数：

- `src/types.ts:30-67`

输入校验只检查字符串形状：

- `src/config.ts:148-204`

随后直接执行：

- `src/evaluator.ts:224-259`

也就是说，下面的输入当前会被接受：

```json
{
  "evaluation": {
    "command": "bash",
    "args": ["-c", "printf probe"]
  },
  "environment": {
    "NODE_OPTIONS": "--require=./src/hook.cjs"
  }
}
```

我实际调用 `normalizeRunPolicy()` 验证过，输出保留了上述 `bash -c` 和 `NODE_OPTIONS`。

所以这里准确的性质只是：

> argv 不经过 Host 的隐式 shell 字符串插值。

它并不意味着：

- command 不是 shell；
- command 被允许列表约束；
- evaluator 经用户 approval；
- evaluator 运行于 DSH sandbox；
- evaluator selection 由 Host 配置固定。

DSH 官方 subprocess 契约本身也明确说明：消费者如果想使用 shell，可以直接传 `['bash', '-c', command]`。而 DSH 架构要求需要进程隔离的消费者使用 `ctx.sandbox` 包装 argv；本插件目前直接使用 `ctx.subprocess`。

### 影响

“trusted host owns evaluator”目前只对**执行和 metric parsing**成立，对**evaluator selection**不成立。

一次被允许的 `autoresearch` 调用，可以成为绕过普通 Bash 工具审批/沙箱路径的任意用户权限进程入口。

### 建议

不要让模型提交任意 evaluator argv。更安全的接口应是：

```ts
evaluation: {
  evaluator_id: "benchmark-v3"
}
```

然后由部署配置映射为：

```ts
{
  executable: "/absolute/trusted/path",
  argsTemplate: [...],
  environmentAllowlist: [...],
  evaluatorFiles: [...],
  datasetIdentity: ...
}
```

并通过 DSH sandbox seam 运行。

## P1：`provenance.dataset` 目前是坏的，使用它会产生固定的 provenance mismatch

初始化时：

- `src/controller.ts:147-153`
- `src/controller.ts:432`

把 dataset label 放进 provenance：

```ts
dataset: { dataset: policy.provenance.dataset }
```

但实际 attempt 调用 `runEvaluator()` 时：

没有传入 `dataset`。

`runEvaluator()` 会重新计算 attempt provenance：

所以初始化 hash 和实际 attempt hash 不同，之后：

```ts
if (evaluation.provenanceSha256 !== r.provenanceSha256)

会进入 `provenance-mismatch`：

- `src/controller.ts:308-310`

我对两条实际哈希路径做了探针验证：

{
  "sameHash": false,
  "initial": "689912900fd9623f3f329550fe3cec87046670eacc9818889c609469968c6d0e",
  "attempt": "ecbf91a3548a91e5c898ec15b650441ffca2af941b8492fbd500b8baf3cdc1fe"

```

### 影响

README 中公开支持的：

```json
{
  "provenance": {
    "dataset": "dataset-v1"
  }
}
```

实际上会使 baseline 失败，而不是提供可恢复的数据来源身份。

### 建议

- controller 调用 `runEvaluator()` 时传入同一份 canonical dataset metadata；
- 添加 controller-level integration test，而不是只测试 `freezeEvaluatorProvenance()`；
- 测试 baseline、candidate 和 resume 三条路径的 hash 完全一致。

## P1：evaluator-file freezing 能力存在，但生产 controller 没有接上

`src/evaluator.ts` 支持：

```ts
evaluatorFiles?: readonly string[]
```

并能：

- 拒绝 symlink；
- 绑定 inode/dev；
- hash 文件内容；
- spawn 前后重新验证。

但 controller 创建 evaluator boundary 时：

```ts
createEvaluatorBoundary(..., {
  evaluation,
  normalizedPolicySha256,
  runId,
  attemptId
})
```

没有传 `evaluatorFiles`：

- `src/controller.ts:149-150`
- `src/controller.ts:279-282`

公开的 `provenance.evaluator` 也只是一个普通 label：

- `src/config.ts:203`
- 没有作为 path 校验；
- 没有传给 `evaluatorFiles`；
- 没有内容 hash。

我实际验证了 controller 当前使用方式对应的 provenance 行为：

1. 创建 `score.mjs`；
2. 计算 provenance；
3. 将它改成输出伪造的极优 metric；
4. 再次计算 provenance。

结果：

```json
{
  "sameHash": true,
  "evaluatorFileHashes": {}
}
```

### 影响

例如：

```json
{
  "mutable_globs": ["scripts/**"],
  "evaluation": {
    "command": "node",
    "args": ["scripts/score.mjs"]
  },
  "provenance": {
    "evaluator": "scripts/score.mjs"
  }
}
```

如果文件名不是 `eval*` / `evaluator*` 等正则保护名称，proposal agent 可以修改 scorer，而 provenance 不变。

这会直接破坏 autoresearch 的根本不变量：

> Agent 可以修改候选实现，但不能修改裁判。

### 建议

最佳方案仍然是 Host 预注册 evaluator。至少也需要：

- 将 evaluator files 变成 config-owned、安全相对路径列表；
- 自动排除出 `mutable_globs`；
- baseline、candidate、resume 均 hash/revalidate；
- 对 dataset files 做相同处理；
- 不要试图从任意 argv 自动猜测 evaluator 文件。

## P2：候选实验一旦 crash/timeout，整个 run 就结束

候选 evaluator 失败时：

- experiment 进入 `crashed` / `timed-out`
- run 进入 `deciding`

然后 cleanup reconciliation 把整个 run 转为：

```ts
round-failed
```

证据：

- `src/controller.ts:331-337`
- `src/controller.ts:353-356`

这与原始 autoresearch 不同。原始 `program.md` 明确要求：

- crash 记录为 crash；
- 简单错误可以修复重跑；
- 根本失败则 discard；
- 然后继续下一实验。

### 影响

无人值守搜索很脆弱：

- 一个 typo；
- 一次 OOM；
- 一次 evaluator 非零退出；
- 一次 timeout；

都会提前结束整晚的研究任务。

这更像“严格事务型实验流水线”，不像“持续自主研究”。

### 建议

对已经证明进程树 quiescent 的 candidate failure：

1. 记录 `crashed` / `timed-out`；
2. 恢复 accepted worktree；
3. 消耗一个 experiment budget；
4. 回到 `ready`；
5. 将错误摘要交给下一 proposal child。

只有以下情况才应该 terminal/block：

- 进程存活不确定；
- evaluator provenance 不可信；
- Git/state evidence 矛盾；
- controller infrastructure 无法安全恢复。

## P2：fresh proposal agent 没有真正的研究记忆

每轮报告要求包含：

- hypothesis
- intended edits
- implementation summary

见：

- `src/agent.ts:78-82`

但 controller 收到后，除 `blockerClaim` 外全部丢弃：

- `src/controller.ts:235-245`

下一轮 history 只有：

- ordinal
- state
- commit
- metric
- decision
- failureCode

见：

- `src/agent.ts:42-50`
- `src/controller.ts:442`

TSV 也没有 description/hypothesis：

- `src/tracker.ts:299-303`

同时 proposal child 没有 Bash，因此即使 history 给了 rejected candidate commit，它也很难查看那个历史 commit 的 diff。

### 影响

新的 child 只知道：

> 第 7 次失败了，metric 是 1.24。

但不知道：

> 第 7 次尝试的是增大 batch size，因 OOM 失败。

于是容易：

- 重复失败实验；
- 无法组合接近成功的尝试；
- 无法根据 crash 日志修复；
- 无法形成长期研究策略。

### 建议

将报告作为明确的 **untrusted annotation** 持久化，不参与 metric 决策，但用于后续研究：

```ts
{
  hypothesis,
  actualChangedPaths,
  implementationSummary,
  candidateCommit,
  metric,
  decision,
  failureCode,
  boundedEvaluatorDiagnostic
}
```

后续 child 至少应得到：

- 最近实验描述；
- 实际 changed paths；
- metric/decision；
- bounded stderr 摘要；
- 可访问的 rejected diff 或结构化 diff summary。

# 四、与原始 autoresearch 的符合度

| 原始原则 | 当前项目 |
|---|---|
| baseline-first | 完整实现 |
| 单一 scalar metric | 完整实现 |

# 五、最终判定

## 可以诚实宣称的内容

> dsh-autoresearch 是一个 DSH 原生的、baseline-first、单指标、有界、Git 隔离、SQLite 可审计并支持保守恢复的实验控制器。

这句话成立。

## 目前不应宣称的内容

> 它已经是可信、安全、可长期无人值守的通用 autoresearch 插件。

这句话目前不成立。

达到该目标前，至少需要完成：

1. **Host 配置固定 evaluator；禁止模型提交任意 command/env。**
2. **通过 DSH sandbox 执行 evaluator。**
3. **修复 dataset provenance 的初始化/attempt 不一致。**
4. **将 evaluator/data 文件真正绑定、保护并重验。**
5. **candidate crash/timeout 后继续搜索，而不是 terminal。**
6. **持久化 hypothesis、summary、diff 和 bounded diagnostics。**
7. **修复 terminal replay，补充支持平台声明。**

这些修完后，项目才会从“优秀实验执行器”跨到“真正的 autoresearch 系统”。

按仓库规则，我已把三条可复用的审查结论补充到 `AGENTS.md`；未修改业务实现。
